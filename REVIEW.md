# Review guide

For `/code-review`, `/security-review` and any agent reviewing a MediaHub change. CLAUDE.md has the rules. This file says what matters when checking a diff against them.

## What failure looks like here
In order of severity:
1. **It leaks.** An Arr API key, session token, password hash or upstream URL reaches the browser, a response body, a log line or the repo.
2. **It lets someone in.** A route handler, server action or page returns data or performs an action without `requireRole(...)` or a server-side session check. A requester can do something admin-only. Input reaches a typed client without Zod validation.
3. **It proxies.** Something forwards arbitrary paths, methods or query strings to Radarr/Sonarr instead of calling one explicit typed client function.
4. **It lies.** The UI shows state that disagrees with Radarr/Sonarr, merge logic drops or duplicates items, or a doc or comment says something the code doesn't do.
5. **It won't run on the NAS.** It adds a service or a heavy dependency, breaks the build without env vars, or assumes a host other than `BETTER_AUTH_URL`.

## Skip these paths
- `src/server/arr/generated/**` and `openapi/**` are generated from the upstream specs.
- `drizzle/meta/**` is generated by drizzle-kit. Do review `drizzle/*.sql`.
- `package-lock.json` should only be checked for unexpected new packages.

## Already enforced, so don't re-check
These are covered by lint, so don't report them by hand:
- `import "server-only"` at the top of every `src/server/**` file;
- no `process.env` outside `src/server/env.ts`;
- lint, typecheck and test failures, which CI catches;
- every `(app)` page starting with `await requirePageUser(...)` and allowing the roles listed in `PAGE_ROLES`, which `src/app/(app)/pages-auth.test.ts` checks. That test catches a forgotten or wrong check, not a deliberate bypass of the test itself, such as shadowing or aliasing the name. Don't report ways to fool it. Gary's diff read on High-risk changes covers deliberate bypasses.

## How to report
- **Every finding needs evidence.** Give a file and line, and a concrete scenario (input or state, then the wrong outcome). Don't guess from a function name or a file name.
- **Tag each finding:**
  - **Important** for a real bug or security issue in this diff;
  - **Nit** for style or cleanup;
  - **Pre-existing** for a bug in code this diff didn't change. Report it, but don't blame this change for it.
- **At most 3 Nits per review.** Drop the rest.
- **Flag the class, not the instance.** If one bug pattern occurs in several places, report it once and list every location.
- **Start the summary with a count**, e.g. "2 Important, 1 Nit". If there's nothing to fix, say so plainly.

## Review rounds
- **Round 1** reviews the whole change.
- **Round 2 onward** reviews only the diff since the previous round. Don't repeat findings already reported, and don't report Pre-existing issues again.
- **After round 3**, stop. Write down what keeps going wrong and rethink the approach instead of patching again.
